# Feasibility and decisions

**Recommendation.** Build a read-only coverage assessor for one Linux host, multiple long-lived HotSpot JVMs and the upstream `java-sql-inj` shield. Use normal signed Shirudo deployment and service-owner restart for remediation. The [controlled-lab qualification](../LINUX-VALIDATION.md#complete-fresh-cohort-qualification-2026-11-27)
demonstrated that two JVMs can disagree under one valid host measurement, with
evidence identifying which cooperative JVM answered. Generalizing beyond that
tested process/path/startup configuration remains open. General live installation and verified in-place removal have unresolved authority and correctness requirements. The findings use [the pinned upstream study](UPSTREAM-ANALYSIS.md). Except for that explicitly recorded qualification, unexecuted design choices and
test scenarios below remain proposals.

## Capability decisions

| Capability | Feasibility at this revision | What an operator can conclude |
|---|---|---|
| Discover JVMs | Feasible within a declared process/credential namespace. Combine Linux enumeration, launcher identity, optional evidence of a mapped JVM library, and service ownership. Names alone can be misleading. | A bounded inventory, including unreadable candidates, expected workloads missing from view, and discovery coverage limits. |
| Detect a missing guard | Conclusive for the chosen *operation* in a controlled cooperative target when a known-discriminating input returns the baseline result and its control passes. In an arbitrary JVM, startup flags or missing diagnostics support only limited findings. | “The intended behavior was absent for this process, path and interval.” General agent absence remains unknown. |
| Correlate measurements | Feasible with independently expected host state, a fresh pinned-key verification and observations on the same process lifetime. Evidence can conflict and is collected at different times. | Two claims with distinct provenance. A successful probe cannot repair a failed host verification. |
| Activate | Startup with the signed installed JAR is upstream-supported. Specific live-capable agents may change a running JVM. No generic signed per-target live transition was found. | Restart is the supported deployment action for the chosen shield. A live change would need a new, explicit authorization design. |
| Roll back | Signed host unload plus controlled replacement of the JVM can establish behavior in a new instance. An instrumented process may outlive that unload. | A before/after comparison with process identities and health controls. An assertion that a previous side effect or transaction has been undone is outside scope. |

## Java mechanism and limits

| Mechanism | What it actually does | Design consequence |
|---|---|---|
| Startup instrumentation | The launcher reads `Premain-Class` and invokes `premain` before application main. Multiple agents run in launcher order. Failure to start a startup agent can abort VM startup. | Include application startup and health in the acceptance test. A manifest attribute or startup banner alone cannot prove that the intended class was changed. [Java agent specification](https://docs.oracle.com/en/java/javase/21/docs/api/java.instrument/java/lang/instrument/package-summary.html) |
| Attach API | The provider can enumerate visible JVM descriptors and establish a connection. `VirtualMachine.loadAgent` passes a JAR location interpreted on the target; an `Agent-Class` entry and `agentmain` are required. `detach` ends the tool connection. Enumeration is provider-dependent. A load can fail during initialization after partial side effects. | Inventory never depends on successful attach. An observation timeout becomes unknown. A returned load call is insufficient evidence of guard behavior. [Attach API](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.attach/com/sun/tools/attach/VirtualMachine.html) · [Agent lifecycle](https://docs.oracle.com/en/java/javase/25/docs/api/java.instrument/java/lang/instrument/package-summary.html) |
| JEP 451 | JDK 21 introduced warnings for dynamic agent loading and prepared for a future default refusal. HotSpot startup policy can explicitly allow or disallow dynamic agent loading. Disabling the whole attach mechanism is a separate policy and can prevent diagnostic attach too. Startup agents remain supported. | Keep dynamic loading disabled for the MVP tests. A read-only diagnostic such as `jcmd <pid> VM.command_line` has separate same-host/effective-UID/GID and attach requirements. Honor those settings. Check the exact vendor/build in any later trial; a JEP announcing a future default does not date that change for every VM. [JEP 451](https://openjdk.org/jeps/451) · [jcmd manual](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html) |
| Retransformation | Requires VM and manifest capabilities and a modifiable target class. A retransformation starts from the specified initial class bytes, reuses prior results of incapable transformers, then invokes capable ones in order. Initial byte representation may differ from the original file. Active frames continue running their old bytecodes. | Use class identity including defining loader and module, and check the method descriptor. A later agent can change the result. An archived class hash or a successful callback cannot establish the currently executing instructions in every thread. [Instrumentation.retransformClasses](https://docs.oracle.com/en/java/javase/21/docs/api/java.instrument/java/lang/instrument/Instrumentation.html#retransformClasses(java.lang.Class...)) |
| Redefinition and removal | Redefinition may change method bodies subject to VM restrictions; ordinary HotSpot disallows typical structural changes such as adding fields/methods or changing hierarchy. Existing static values and live application state persist. Removing a transformer stops future participation; callbacks can race its removal. Bootstrap search additions and module access expansions have no corresponding general undo operation. | Reverting method behavior, unloading an agent and restoring application state are three different contracts. Never restore archived bytes over other agents' changes. [Instrumentation API](https://docs.oracle.com/en/java/javase/25/docs/api/java.instrument/java/lang/instrument/Instrumentation.html) |
| Byte Buddy, ASM and the JDK Class-File API | Byte Buddy supplies typed matchers, advice and resettable transformers with defined reset strategies. ASM offers low-level bytecode visitors/readers/writers; the author owns selection, frames, verification, classfile compatibility and lifecycle. Shirudo's Base64 example uses Java's public Class-File API instead. | Reuse the existing agent implementation. No transformer library in the orchestrator. For a future controlled shield, choose the least invasive library for its required target-JDK range and retain the transformer handle only if the reset contract is designed and tested. [Byte Buddy tutorial](https://bytebuddy.net/partial/tutorial.partial.html) · [Reset contract](https://github.com/raphw/byte-buddy/blob/master/byte-buddy-dep/src/main/java/net/bytebuddy/agent/builder/ResettableClassFileTransformer.java) · [ASM](https://asm.ow2.io/) · [Base64 build](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-base64/build.sh) |

## Which shield to use

**Choose the existing SQL shield, unchanged.** Its Maven build targets release 11, pins Byte Buddy 1.18.12 and H2 2.3.232, and shades the agent JAR. The manifest requests redefine/retransform capabilities but declares only the startup entry point. `RaspAgent.premain` installs advice on concrete JDBC Statement implementations and matching execute-family methods with a first String argument. It discards the returned transformer handle. The advisor is a regular-expression heuristic and logs matching SQL. Never feed customer statements into the test. [Parent POM](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-sql-inj/pom.xml) · [Manifest](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-sql-inj/agent/pom.xml) · [Selection](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-sql-inj/agent/src/main/java/com/security/rasp/RaspAgent.java) · [Advice](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-sql-inj/agent/src/main/java/com/security/rasp/SqlInjectionAdvisor.java)

**Proposed benign discriminator.** In each controlled fixture, use a private in-memory H2 connection and issue two fixed read-only scalar queries through the *same concrete Statement method*. The first returns a plain text constant; the second returns the literal string `OR 2=2` as data. No tables, concatenation, external input or database modifications are involved. The code matches that text even inside a quoted literal. Predict a shield-specific `SecurityException` on the second call when guarded, and the exact scalar otherwise. This deliberately exercises a false positive, which makes it a safe indicator of that advice path. Verify the precise result and exception at the chosen JDK/H2 pin before trusting the discriminator. Both calls returning errors, a wrong scalar, another exception, a timeout or broken liveness makes the probe inconclusive. Success says nothing about SQL injection prevention in general or other drivers/loaders. [Advisor predicate](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-sql-inj/agent/src/main/java/com/security/rasp/SqlInjectionAdvisor.java)

**Why defer the upstream Base64 agent.** Its build uses `--release 24` and the Beefile selects x86-64 for tree deployment. Both agent entry points share `install`, which appends a nested bootstrap helper, checks private JDK structure and retransformation capabilities, retransforms a bootstrap class, and removes its transformer in a finally block. The installed latch survives. A later retransformation can omit the earlier change, and an ordinary repeat install can return early. The helper search path can persist even if installation subsequently fails. No reset method or stable behavior contract for arbitrary JDK builds was found. Its launcher uses the JDK Attach API outside the Shirudo admission/measurement transaction. Existing test t9113 establishes an operator workflow on new JVMs. These are source-derived limitations, not reproduced failures. [Agent](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-base64/src/com/shirudo/base64guard/Base64GuardAgent.java#L76) · [Beefile](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-base64/Beefile) · [Rollout test](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/testing/end2end/t9113-shield-rollout.sh)

## Conditions for future live operations

**Current decision: defer.** A signed JAR establishes provenance. A fresh host measurement establishes a host state. Neither delegates authority to modify a specific running service. Enabling dynamic loading gives that target a general JVM facility rather than an allowlist of Shirudo JARs. Resolving a pathname in the caller and opening it later inside the target also admits PID reuse, namespace differences and legitimate unload/replacement races. A before/after digest check can detect some races, but cannot make the target's open atomic with authorization. A compromise of the target can forge a receipt. [Java verification](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/util/upatch_verify.c#L110) · [Attach path semantics](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.attach/com/sun/tools/attach/VirtualMachine.html#loadAgent(java.lang.String,java.lang.String))

A concrete narrower research alternative is a **startup-loaded, operator-signed, shield-specific guard** with fixed pre-reviewed behavior and an explicitly authorized mode transition. This would be a new shield/protocol, not a Shirudo feature. Such a transition still changes security state without a native per-JVM measurement. Before accepting it, require a maintainer-reviewed authority model, service-owner opt-in, bounded target identity and artifact/version binding, protection against command replay, serialized transitions with crash recovery, independent host verification, and a demonstrated same-process control/probe. Document whether deactivation can be abused to defeat the required mitigation. Never distribute signing keys to a target or grant an in-process peer authority to publish host measurements. If those gates cannot be met, retain restart-only operation.

For any proposed **in-place behavioral rollback**, require a signed, reviewed lifecycle contract for exactly one transformation, no structural edits, controlled loader set, explicit interaction with other agents, a quiescence policy for old frames, and recorded remaining state. Test duplicate requests, failure between registration and retransform, concurrent class loading and another agent's transform. If the history is ambiguous, return “restart required.” Even a valid after-probe covers only new invocations of the tested path.

## Windows development and Linux validation

**This workstation.** Windows reports Windows 11 Home Single Language (64-bit), firmware virtualization enabled and a hypervisor present. The only registered WSL distribution at review was a stopped Docker Desktop distribution. Microsoft excludes the Hyper-V role from Windows Home. The recommended arrangement here is Windows for editing, Maven and pure-Java tests, with an x86-64 Linux KVM operator reached over SSH hosting the single Shirudo target VM. A separate Linux system is a lab prerequisite for this recommended route. No guest was booted during the study. [Microsoft Hyper-V installation requirements](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/install-hyper-v) · [Upstream operator prerequisites](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/start/quickstart.rst)

**Local alternative to qualify.** On a supported Windows Pro/Enterprise machine with suitable hardware, an outer Hyper-V Linux VM could serve as operator if virtualization extensions are exposed while it is powered off. A user-managed Linux VM on this Home machine could also be evaluated if its hypervisor exposes nested KVM. The acceptance gate in either case is a readable/writable `/dev/kvm` in the Linux operator **and** an actual inner Shirudo guest boot with fresh evidence. A WSL distribution, a generic container or the Windows hypervisor flag alone cannot establish this. [Microsoft nested virtualization prerequisites](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enable-nested-virtualization)

Use the pinned quickstart sequence on Linux: `testing/vm/kernel-artifact.sh fetch`, `make`, `make shirudo-build`, then `make -C testing vm VM_NAME=quickstart` and `make -C testing vm-ssh VM_NAME=quickstart`. Stage the kernel matching the checkout, verify its digest, allow upstream locked memory, and supply the documented compiler, OpenSSL 3.5+, QEMU, swtpm, dracut and build-container prerequisites. The protected guest needs the signed-loader ABI, Shirudo kernel hooks, BPF LSM, compatible initrd/trusted image and TPM 2.0. Install/pin the test JDK and H2 fixture separately as ordinary workload software. Store signing keys outside guest-visible shares. Save kernel build metadata, runtime version ID, JDK build, verifier policy and private test-TPM identity provenance with each run. [Requirements](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/operate/plan/system-requirements.rst) · [VM role separation](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/testing/vm/run.sh#L2007) · [Kernel selector](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/testing/vm/kernel-artifact.sh)

**Validation boundary.** The quickstart directly boots kernel/initrd and emulates the TPM. It lacks production signed-UKI boot-phase measurements in PCR 11. Reverting a guest together with software TPM state can revert its history. Label reports “development VM”; use an independently provisioned measured boot chain and hardware-backed enrollment for production claims. [Quickstart boot differences](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/start/quickstart.rst) · [Upstream verifier assumptions](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/security/threat-model.rst#L2280)
