# Threat model for JVM coverage evidence

**Claim under review.** Given a trusted operator policy, a properly enrolled target and independently verified Shirudo evidence, Kintsugi can report that a particular cooperative JVM exhibited a specified guard behavior during a bounded observation window. Each clause is required. Shirudo authenticates host measurements; Linux supplies local process identity under the observer's trust assumptions; the JVM supplies an observation of one code path. There is no hardware-authenticated link from the quote to the executing Java method. An arbitrary or hostile JVM may yield only “unknown.” This document describes a proposed system. ## Assets, actors and privilege

| Trust domain | Assets and authority | Required privilege for the MVP |
|---|---|---|
| Operator / verifier | Owns approved source/build records, process intent, expected state, enrolled AK/EK references, challenge freshness and retained results. Compromise here invalidates attribution. | Run the official verifier on a separate trusted Linux operator. Build/sign with the authorized upstream helper and protected key separately from assessment. The report generator needs readable approved references; no private signing key. |
| Target boot/runtime | Kernel, initrd, sealed keyrings, dm-verity runtime, LSM seal and TPM underpin upstream admission and measurement within its published threat model. | Target administrator invokes authenticated Shirudo CLI with its documented privileges and memory-lock limit. Root alone does not turn an arbitrary executable into the trusted runtime. Local report collection has no authority to write the eventlog or extend the register. |
| Service owner / supervisor | Declares which instances should receive which guard, controls the launcher, chooses restart window and can authorize fixed test calls on its own fixtures. | Dedicated non-root fixture UID. The supervisor can launch and observe its own child processes over inherited pipes. Runtime startup options and fixture binaries are approved inputs. |
| Target observer | Reads visible procfs information and imports allowlisted observations. An optional diagnostic needs matching effective UID/GID and attach permission for that target. | Ordinary user within the intended PID namespace. Other UIDs, restricted `/proc`, missing tools or disabled attach may restrict coverage. Report those bounds; never give the observer broad ptrace, BPF, TPM or root authority. |
| JVM, libraries, other agents | Can fabricate logs/probe answers, alter properties, load another class with the same name, or change behavior through another transformer. Same-user hostile processes may also attack the observer. | Treat these as cooperative only for the bounded behavior claim. No signing key, verifier secret or host administration authority goes into the JVM. |
| Developer / hypervisor | A Windows administrator, operator VM administrator or VM snapshot controller can alter the guest or software TPM. | Lab trust includes these actors. A VM snapshot and its swtpm are development inputs. Production assurance requires a separately justified hardware/boot/enrollment profile. |

Shirudo's ADV-B is root on the target without the operator's key. T15 protects the Java artifact in the enforced host configuration. R1/R2 allow use of existing signed directives and the actual runtime command interface; R24 permits launching JVMs without the guard and repudiates resistance to a hostile application. Kintsugi adds visibility to honest-operator drift. It does not elevate JVM observations to the root-resistant properties of a sealed host artifact. ## Evidence and adversary capabilities

| Observation | Adversary or ordinary failure | Required interpretation / response |
|---|---|---|
| Archive matches installed JAR; `status` verdict is OK | Status is target-produced. No JVM may have consumed the options; the manager can still have its earlier environment. | Record host-local installation and check a specific intended process. Preserve status conditions independently of verifier outcome. |
| Fresh TPM quote and certification | Replay of old reports, an unpinned AK, correct AK on a different boot, wrong config, or advice to trust whatever chain the target reported. | Use independent trust at enrollment, a unique verifier nonce, AK pin, expected deployment state, binding PCR and config policy. Recheck after the process window. Replayed or out-of-policy evidence precludes verified host attribution. |
| Eventlog, host clock, boot ID, “bound in initrd” text | Some fields are supplementary target reports. Replaying event digests authenticates covered fields only. Omissions can affect conclusions about history. | Use official replay, derived-field and register checks; pin expected binding PCR 9/11. `--require-initrd` alone relies on unauthenticated text. Do not use reported wall-clock load time to prove a process started after installation. [Verifier caveats](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/security/threat-model.rst#L1999) |
| Sealed-path argument at startup | An unload leaves a no-op JAR under the same name. A legitimate replacement can change contents later. A mount namespace can present a different file at the same path. | Track payload digest and actual launch context. Scope MVP to one verified mount/PID namespace; conflicting or inaccessible views stay unresolved. Never infer loaded bytes from the current pathname. |
| Process enumeration and supervisor record | PID reuse, exit, exec, duplicate service names or procfs filtering. An embedded JVM can have a non-Java executable. | Check stable lifetime and ownership before/after collection. Use direct child handles for fixture probes. On ambiguity discard the association. Keep expected-but-unseen workload slots visible. |
| Challenge returned by a JVM | A hostile JVM can echo a fresh nonce, recognize a test, emulate a shield or delegate work. An application may log success even when a JDBC call was never intercepted. | A nonce gives freshness under cooperative assumptions, not honesty or code identity. Bind to the supervised channel; require an independent harmless control and correct effect. Limit the claim to that fixture, loader, method, process lifetime and time window. |
| A valid signature or matching payload in a package | A valid signed upatch can be obsolete for this target, or the package can carry untrusted auxiliary content. A signer compromise can authorize harmful code. | Check operator-pinned name/type/payload and upstream revocation state. Obtain auxiliary fixtures from independently controlled builds. Treat the signed shield code itself as privileged within the service. Keep signing outside the target. |
| Signed host retirement and a healthy new instance | An old JVM can survive a rolling restart, a service owner can restart the wrong unit, or a restart can cause an outage. | Report both old and new lifetimes; verify old instances have drained, the new instance passes its benign controls, and the operator's expected instance count matches. A persistent old instance with the guard is a visible discrepancy. |
| Aborted operation, concurrent deployment, verifier timeout | TPM extend, logging, archive, options propagation and application start have different failure points. Options can fail after a load has been measured. | Preserve phase/error, quarantine contradictory results and refresh host/process evidence. Let Shirudo reconcile its own state. Do not auto-repair a tampered verdict or retry a mutation from an observer. [Load failures](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/reference/cli/upatch-load.rst) · [Unload ordering](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/builtin-upatch.c#L3641) |
| Probe/CLI arguments and output | Applications may include secrets in command lines, environment and SQL logs. Unbounded output, arbitrary paths or inherited Java options can corrupt the collector or exhaust the host. | Use fixed local commands, clean supervisor/collector environments, bounded output and deadlines. Normalize the one option of interest in memory; store method outcome and reason instead of SQL/credentials. Protect raw evidence and restrict retention. Use synthetic fixture data only. |

## Verification policy for this design

1. Enroll with upstream EK credential challenge, using an out-of-band EK name or trusted EK CA, and pin the AK after successful activation. In the dev VM record how the operator provisioned that particular swtpm. A pin copied from the target being assessed provides no independent identity. [Challenge](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/reference/cli/attest-challenge.rst)
2. For each independent verification request, generate a new cryptographically random nonce on the verifier and bind it to the assessment and expiration. Use `attest predict` on independently known certificates/boot inventory and ordered post-boot operations for the lab. Match the expected register with `attest verify`; reject unexpected changes in either bracket. Use separately approved firmware/kernel/boot PCRs and binding PCRs, plus `--expect-config-root` with the configured config PCR or NvPCR, according to the profile. Only request strict anchoring in a profile where subsequent PCR 9 use permits it. [Verifier duties](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/security/threat-model.rst#L2280) · [Verify options](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/reference/cli/attest-verify.rst)
3. Execute the verifier in the operator domain and preserve its exit status, JSON verdict, checks, arguments, original evidence digest and profile revision. Some checks are “note” even when the overall verdict is OK. Reject missing pins/expectations at policy construction. A malformed document, stale nonce or unknown schema fails the assessment of host state. Expected production boot facts that the test VM cannot establish must appear as explicit limits on the lab profile.
4. Keep the app observations outside the native attestation document. Hashing an observation into a challenge can associate bytes with a request, but cannot make the TPM inspect the JVM. Any Kintsugi report digest binds a report for comparison, with provenance limited to whoever produced and stored it. Production resistance to observer/target collusion is outside this design.

## Mutation and failure boundary

The read-only MVP adds no code-loading authority. It neither interprets the options file as shell input nor changes service configuration. Admin-controlled upstream signed operations and owner-controlled restarts remain separate audited events. A target that declines inspection remains a valid target with incomplete coverage. A prospective live-agent loader would expand privileges for eligible targets, introduce an in-process control surface and create a time gap between authorization and VM-side file resolution. It needs separate review before any implementation. A signed **host unload** cannot be borrowed as an authorization to run arbitrary “undo” code inside a JVM.

A shutdown, class change or partial behavioral rollback can leave static state, threads, bootstrap helpers, prior IO and outstanding requests behind. A successful second probe establishes the behavior of that new invocation only. If the safety case needs historical side effects undone, an uncooperative application's effective bytecode proven remotely, or protection against hostile target root across all JVMs, this design cannot meet it. Use application recovery/upgrade and Shirudo's appropriate kernel-enforced controls for the corresponding requirements.
