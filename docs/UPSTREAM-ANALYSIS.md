A final remote check and fetch advanced `main` to **`39923c519f601c687a6c95aff40a3733172d5673`**. The complete delta removes one obsolete CI workflow. ## R24 at this revision

**R24 still applies.** Threat T15 protects admission and the installed JAR. The Java load path ends after placing the JAR, archiving and measuring the upatch, and updating startup options. It does not enumerate PIDs, contact JVMs or measure a transformation. The user manager's environment is a delivery mechanism outside the seal. A process already running, a stale user manager, an independently launched system service or an overriding environment can each produce the same measured host state with different JVM coverage. R24 names inspection of JVM arguments as a diagnostic. The application itself can alter its behavior after startup. [T15 and R24](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/security/threat-model.rst#L1981) · [Java load path](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/builtin-upatch.c#L2753) · [Options writer](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/util/java_agent.c#L251)

There is an exception worth preserving in project terminology. The upstream `java-base64` **example JAR** has a dynamic attach launcher and an `agentmain`. A compatible JVM can acquire that guard later. This does not change the semantics of a Shirudo `java_load` event. Conversely, a JVM can retain the effect after the corresponding host unload. The upstream rollout test checks behavior in **new** JVMs on either side of a tree change. Kintsugi's contribution would be detecting divergence in a named population of **already running** JVMs. [Example agent](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-base64/src/com/shirudo/base64guard/Base64GuardAgent.java#L55) · [Rollout test](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/testing/end2end/t9113-shield-rollout.sh) · [JVM launcher used by the test](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/testing/end2end/guarded-jvm.sh)

## Target state machine

1. **Admission.** Under the upstream load protocol, the runtime stages a single input, applies version/platform/chain preconditions as requested, serializes updates, reconciles prior interrupted state and authenticates the Java artifact. `java_apply` hands the verified JAR bytes to `java_agent_install`. The runtime creates or validates the labeled directory and seals the file at `/run/shirudo-java/<name>.jar`, mode 0644. Host root can read the artifact; the seal limits changes by tasks without runtime authority. [Load contract](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/reference/cli/upatch-load.rst) · [Seal and directory checks](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/util/java_agent.c#L96)
2. **Measurement and propagation.** The load artifact is archived at `/var/lib/shirudo/upatches/<name>.upatch`. A typed `java_load` extends the register and is logged. The writer then updates `/run/environment.d/shirudo.conf` with the loaded names in order, appending agent arguments to prior options. Failure to update options is a warning even after a successful measurement. A later environment file can replace the value. Java 8 also has a documented option-length/count limit. [Load ordering and recovery](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/reference/cli/upatch-load.rst) · [Java guide](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/upatches/write/java-agents.rst) · [Typed event mapping](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/util/eventlog.c#L574)
3. **Consumption.** Systemd user managers propagate the environment they obtained to their children. A stale manager can miss a new agent or keep naming a retired one. A system service needs explicit startup configuration. A JVM consumes the startup option only when launched. The SQL demo's launcher explicitly sources the options file, which is a different route from normal manager inheritance. Do not execute this unsealed configuration as shell input in a privileged collector. [Demo launcher](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/upatches/java-sql-inj/sql_inj_vuln) · [Systemd environment semantics](https://www.freedesktop.org/software/systemd/man/latest/environment.d.html)
4. **Retirement.** After directive verification and archive/digest matching, `java_unload_locked` measures `java_unload` first. It retires the JAR by writing a sealed no-op agent at the same path, removes the archive and syncs options. A missing archive has a distinct already-unloaded path. Failure after measurement can leave partial state. A stale launcher can still start successfully using the placeholder. Neither a path's existence nor seeing it in the JVM arguments identifies the effective agent version. [Java unload](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/builtin-upatch.c#L3641) · [Placeholder and sync](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/util/java_agent.c) · [Functional assertions](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/testing/functional/upatch/t3114-java-agent.sh#L132)
5. **Restore.** Init restores eligible archived Java loads and options across boots. A repeat init in a bound boot refuses a missing or changed JAR for an already recorded load. It cannot reconstruct what an earlier JVM ran. On drift, retain the upstream condition and collect evidence before any remediation. [Boot restore](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/builtin-init.c#L995) · [Status conditions](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/reference/formats/status-json.rst)

## Integration surface at the pin

The commands below are upstream syntax. Angle brackets are metavariables. Target commands that access protected state must execute the authenticated runtime image's binary. In the test VM the documented path is `/run/shirudo/runtime/usr/bin/shirudo`. The interactive shell supplies an alias. A program using argument-vector execution needs the actual path. CLI startup also locks memory. **Measurement interpretation.** Enroll the AK using `attest challenge` with an independently trusted EK name or vendor CA, complete credential activation and check it. For a closed lab sequence use `attest predict` with all enrolled certificates, the approved boot set/tree root and the ordered expected events. Java boot entries use `--expect=java:<name>=<digest>`; a post-boot transition uses `--event=java-load:<name>=<digest>` or `java-unload`. Compare the independently predicted register. Blanket acceptance of runtime events does not restrict them to this shield. The verifier checks the nonce-bound PCR quote, NV certification, replay and derived event fields. Uncovered fields including wall time and boot ID are target reports. Status, JVM telemetry and a Kintsugi report are outside this claim. [Predict](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/reference/cli/attest-predict.rst) · [Verification pipeline](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/util/attest.c#L1495) · [Evidence boundary and verifier duties](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/security/threat-model.rst#L446)

**Telemetry boundary.** The Java guide routes agent telemetry through JVM facilities. The BPF LSM restricts retrieval of BPF objects and program test runs to Shirudo. Giving a JVM access to Shirudo's maps or adding its observations to the host register would change that boundary. [Upstream agent telemetry limits](https://github.com/shirudo-dev/shirudo/blob/39923c519f601c687a6c95aff40a3733172d5673/Documentation/upatches/write/java-agents.rst)
